**TL;DR.** K16S is a self-hosted, timed CKA/CKS mock-exam simulator for humans. It has 87 tasks (CKA 36, CKS 51, no CKAD). Each task is a YAML metadata file plus a `setup.sh` and a `validate.sh`, executed as root by a small Go server. The cluster is built with kubeadm. **The control plane runs on the host VM itself.** Workers are **privileged Incus LXC system containers** with real systemd, containerd and kubelet. Three deployment modes exist: VPS with Incus, a Lima laptop VM with the same stack, and a kind-based "lightweight" mode. A capability tag (`requires: heavy`) removes tasks that a mode cannot support from the score denominator. There is **no per-task reset**. Control-plane faults are injected into the same host that runs the grader. Whole-cluster reset means a full rebuild, and Incus snapshots are never used. Validators are hand-written bash, often structural rather than behavioural, with a hard 30 s timeout that is shorter than several validators' own polling loops. For KOPS, K16S is valuable for three things: the task-triple convention, the capability/denominator idea, and the concrete list of kernel and container settings a kubelet-in-container backend must handle. Its environment topology is the thing KOPS must *not* adopt (R1 in `docs/backend-design.md`).

## 2. Runtime lifecycle

1. **Provision (once).**
   - An installer either runs the provisioner locally, rsyncs it to a remote host, or delegates to the Lima or kind wrapper (`install.sh`).
   - Step order (`provision/main.sh:59-84`):
     1. preflight: OS and resource checks; disable swap; rename the host
     2. host kernel modules and sysctls
     3. containerd
     4. Incus install, plus a *background* base-image prefetch
     5. kubeadm packages, then `kubeadm init`
     6. Calico, then metrics-server
     7. create the workers, then a parallel in-container package install and a parallel join
     8. sshd on the workers
     9. candidate user
     10. terminal, then nginx
     11. build and start the server
     12. profile extras (etcdctl environment variables)
   - The only timing statement in the code is that `kubeadm init` takes about 2 minutes (`provision/cluster-init.sh:50`).
2. **Task discovery.** At startup the server treats each subdirectory of the exam directory as a profile and parses every `*.yaml` in it. The id falls back to the filename stem (`server/questions.go:26-71`). Adding a task requires copying files and restarting the server.
3. **Session.** Starting a session ends any active one and records profile and duration. The countdown runs client-side (`server/handlers.go:73-111`, `+page.svelte:120-128`).
4. **Setup (per task, user-triggered).** The Setup button runs the task's `setup.sh` as root on the host with the admin kubeconfig and a 60 s timeout. Afterwards, new top-level `/opt` directories are handed to the candidate user (`server/handlers.go:196-287`). Nothing is set up automatically at session start.
5. **Solve.** The candidate works in the host shell as `candidate`, or over ssh to workers as root.
6. **Check.** The Check button runs `validate.sh` (30 s timeout). Exit code 0 means pass. Output is stored, and the last check wins (`server/handlers.go:147-193`, `server/store.go:141-151`).
7. **Score.** Computed in the browser as the weight of passed tasks over the weight of *scorable* tasks (`+page.svelte:34-46`).
8. **Cleanup.** None per task (§6).

## 3. Scenario/task representation

**Layout.** One metadata file per task at `exams/<profile>/<NN-slug>.yaml`. Its scripts live in `exams/<profile>/scripts/<NN-slug>/` as `setup.sh` and `validate.sh`. The id, the filename stem and the script directory must match (`DOCS.md:375-397`).

**Schema** (`server/questions.go:12-24`):

| Field | Type | Meaning |
|---|---|---|
| `id` | string | Task id. Defaults to the filename stem |
| `title` | string | Display title |
| `weight` | int | Relative points (observed 3–8) |
| `context` | string | `""` or `controlplane`. Display-only hint that host access is needed |
| `description` | Markdown | Task statement |
| `hint` | Markdown | Optional hint. **In practice often a near-complete solution** |
| `requires` | string, optional | `heavy` means the task needs the VM+Incus stack. It is excluded in lightweight mode |

**Structural example** (paraphrased from `exams/cka2/01-fix-apiserver.yaml`, not copied):

- *Metadata*: id `01-fix-apiserver`, weight 8, context `controlplane`. The description says the API server static-pod manifest has two injected defects and asks the candidate to fix them and write evidence to a file under `/opt/cka2/`. The hint explains the client-vs-peer etcd port distinction.
- *Setup*: backs up the manifest, then edits it in place to point the etcd client URL at the peer port and to add an unknown flag.
- *Validate*: polls API reachability, greps the manifest for the corrected URL and the absence of the flag, and checks that the evidence file exists.

**Conventions.**
- Answers are usually *evidence files* under `/opt/<exam-dir>/`.
- Most validators combine a live-state check with an evidence-file check.
- There is **no reference-solution artefact**; only the `hint` exists.
- Of the 87 tasks, 10 carry `requires: heavy` and 43 carry `context: controlplane`.

## 4. Environment abstraction

| Aspect | Full: VPS/VM + Incus | Laptop: Lima VM | Lightweight: kind |
|---|---|---|---|
| Entry point | `install.sh` (local or `--host`) runs the provisioner | `local/k16s-local up` creates a Lima VM and runs the same provisioner inside it | `lightweight/k16s-lite up` |
| Control plane | Host OS (Debian 13 / Ubuntu 22.04–24.04) | Ubuntu 24.04 guest | kind control-plane container (repo bind-mounted) |
| Workers | Privileged Incus LXC | Same, inside the VM | kind worker containers |
| Kubernetes node names | `controlplane`, `node01..` | Same | kind defaults. Only the ssh aliases are `node01..` [static inference] |
| Grader path to workers | `incus exec` | `incus exec` | None. The CP container has no Docker socket, so worker-touching tasks must be `heavy` |
| AppArmor | Host kernel (tasks pin pods to `controlplane`) | Same | Unavailable |
| Minimum resources | 4 vCPU / 8 GB / 20 GB free (enforced) | 4 vCPU / 8 GiB / 30 GiB VM; 16 GB host recommended | ~2 GB (documented) |
| macOS | Client only | Yes (vz, arm64; no nested virtualisation needed because workers are LXC) | Yes (Docker Desktop) |
| Whole reset | Uninstall + reinstall | Delete VM + reprovision. Lima snapshot/revert with the qemu driver only | `kind delete` + `up` |
| CI suitability (assessment) | Possible on a root Linux VM runner; not implemented | Needs nested virtualisation | Good |

Observed cross-mode defects [static inference]:
- In lightweight mode, tasks that hard-code `node01`, `node02` or `controlplane` but are **not** tagged `heavy` should fail. These are `cka/03`, `cka/07`, `cka/16`, `cka2/08` and `cks2/10`, plus seccomp tasks that instruct pinning to `controlplane`.
- With the default of one worker, `cka/03` needs `node02` and cannot pass in any mode.

## 5. Verification model

- **Grader on the host.** Every validator runs as root on the control-plane host (or in the kind CP container) with the cluster-admin kubeconfig. Worker state is read via `incus exec`, never ssh (`server/handlers.go:166-177`). The grader therefore depends on the health of the very control plane that tasks deliberately break. An unfixed API server fault makes every later check fail. The grader also shares a filesystem and user namespace with the candidate's shell.
- **Style.** Hand-written bash. Each check prints a specific failure reason and exits 1. JSON and YAML are parsed with inline Python.
- **Check kinds.**
  1. Live API state (Running, Bound, Ready).
  2. **Structural spec inspection.** For example, NetworkPolicy validators assert ports and selectors in the object. **None probes live connectivity.** No validator execs into a pod.
  3. Grep of host files: static-pod manifests, kubelet config.
  4. Evidence files, sometimes accepted on a single keyword (e.g. `cka/09`).
  5. Tool-based verification: etcd snapshot status, openssl parsing, AppArmor status.
- **Timeout-vs-polling bug.** The server kills validators after **30 s** (`server/handlers.go:172`). Several validators poll longer:
  - `cka2/01` and `cka2/13`: up to 120 s
  - `cka2/02` and `cka2/04`: 90 s
  - `cka/04`, `cka/10` and `cka2/11`: 60 s

  A correct but slow recovery, such as a static-pod restart after a manifest fix, can be scored as FAIL. The result depends on timing.
- **Weak or incorrect checks.**
  - `cka/07` computes the set of non-DaemonSet pods left on the drained node but never uses it, so the drain itself is not verified.
  - `cks3/06` and `cks3/08` check the kubelet config file but not the running kubelet's behaviour.
  - `cks3/01-02` compare the candidate's count against the candidate's own saved output.
- **Environment assumptions.** kube-bench is referenced at a fixed path but never installed. Two setups fetch artefacts from the Internet: Gateway API CRDs and the Helm installer. No Ingress or Gateway controller is installed, so those tasks are structural only.
- **Tests.** One Go unit test lints that any script invoking `incus exec` belongs to a `heavy` task (`server/questions_test.go`). There is no golden-solution test and no CI.

## 6. Reset/cleanup model

- **Per task: none.** There is no teardown hook.
  - Some setups pre-clean their own leftovers, e.g. `cka/10`, `cka/14`, `cka2/17`.
  - Others are not idempotent. Re-running `cka2/01` setup duplicates the injected flag and overwrites its backup with the broken manifest.
  - State accumulates across tasks in one shared cluster.
- **Per session: none.** Ending a session only timestamps it (`server/store.go:109-112`).
- **Whole environment: rebuild.**
  - Lima: delete and recreate the VM, then fully reprovision.
  - kind: delete and recreate the cluster.
  - VPS: a long reverse-order teardown (services, Incus, kubeadm reset, iptables flush, Calico interfaces, packages, hostname and swap restore; `provision/teardown.sh`), then reinstall.
  - The docs justify the rebuild by the fragility of stale kubeadm/kubelet state on rejoin (`DOCS.md:145`).
  - The only faster option is a whole-VM Lima snapshot on the qemu driver.
  - Incus snapshot/restore/copy is never used.
  - Expected reset time is minutes [static inference]. No timings are recorded.

## 7. What is useful for KOPS

**7.1 Ideas (re-implement independently).**
1. **Task triple by convention.** Metadata + setup + validate, discovered by directory layout. KOPS extends this with an explicit reference solution and a machine-readable result (`docs/scenario-schema.md`).
2. **Capability tag + denominator exclusion.** A task declares the capability it needs (`requires: heavy`). Backends that lack it neither run nor count the task, so 100% stays reachable on every backend. KOPS generalises this to backend class ordering (`kind` < `kind-node` < `vm`) plus feature sets, and reports **per-class denominators** (`docs/backend-design.md` §6).
3. **Lint that ties tags to backend-specific commands.** KOPS should keep such a lint and add a golden-solution CI gate: setup→validate must FAIL, and setup→solution→validate must PASS.
4. **A separate privileged grader channel.** Grading reaches node internals through the host-side runtime (`incus exec`), not through the candidate's ssh path. KOPS keeps the agent channel and the grader channel distinct.
5. **Specific failure messages** per check. KOPS makes them structured, per-assertion records.
6. **Engineering details.** Idempotent provisioning steps with markers. Parallel node bootstrap. A background image prefetch overlapping kubeadm init. Evidence-file plus live-state dual checks.

**7.2 Checklist: what a kubelet-in-container backend must handle** (derived from the LXC settings K16S applies, `provision/incus.sh:71-94`, `provision/node-join.sh:31-47,116-117`). K16S's handling is described in prose here. KOPS B1 and B2 must each take an explicit position on every row.

| Concern | How K16S handles it (privileged LXC) | Fidelity consequence | Relevance to KOPS |
|---|---|---|---|
| `/dev/kmsg` for kubelet | Passes the host device into the container | Works, but the node reads the host kernel log | B1: kind already handles this. B2: native |
| Kernel modules (overlay, br_netfilter, iptables, conntrack) | Loaded on the host at container start. In-container modprobe fails and is ignored. kubeadm SystemVerification preflight is skipped | Module state is host-global. "Load a module" tasks are impossible | B1 limit, recorded in metadata. B2 native |
| sysctls | Written inside the container. Errors ignored. `/proc` and `/sys` mounted read-write | Netns sysctls work. Others are host-global and writable from the node | B1: read-only `/proc/sys` outside netns. B2 native |
| Swap | Disabled on the host only. No kubelet swap setting | Swap tasks cannot be modelled per node | B2 only |
| cgroups | Host must be cgroup v2. Container cgroup mount forced read-write. systemd driver in kubelet and containerd | Works through delegation. No container limits, so every node reports full host capacity [static inference] | B1: set per-node limits or document capacity. B2: VM sizing |
| overlayfs snapshotter | Relies on a `dir` storage pool (host ext4) and privilege | Would break on other pool drivers without extra config | B1: kind handles it. B2: native |
| AppArmor | Containers run unconfined. Pods needing AppArmor are pinned to the host control plane | Nested AppArmor is unavailable on workers | B1 limit. B2 native |
| Seccomp | No special handling. Profiles are node-local files | Works | Both |
| Capabilities / privilege | Privileged, nesting on, no capability drop | No security boundary: node root equals host root | KOPS must not expose a host-root path to the agent |
| kube-proxy conntrack | Not configured (kind does configure it) | Possible failure writing conntrack limits from a non-init netns [static inference] | B1 inherits kind's handling |
| systemd / journald | Full systemd in the image. Boot is detected via the system-running state | Real `systemctl`/`journalctl`. The main ergonomic win | B1 (kind image has systemd). B2 native |
| sshd | Must be installed (image ships the client only). Key-only root | Works | B1 derived image adds sshd |
| Reboot resilience | Autostart set, yet docs warn nodes may come up stopped | Fragile | B2: reboot is a first-class feature |
| Node failure | Only a kubelet stop is used | Hard failure (container stop/freeze) is available but unused | B1: container stop/pause. B2: VM stop |

**7.3 Coverage lesson.** Only 2 of 87 tasks exercise a *worker's* system layer (stopped kubelet; static pod). Every other system-level task (API server, scheduler, etcd flags, kubelet hardening, AppArmor) was placed on the host control plane. Even K16S's authors avoided the shared-kernel limits by moving hard tasks onto the non-resettable host. KOPS should treat that as evidence for placing the control plane inside a resettable unit.

## 8. What should NOT be copied

- **Topology.** Running the control plane on the host, with privileged LXC workers, as the benchmark substrate (see §10).
- **Isolation.** No per-task reset, and shared mutable state across tasks.
- **Blast radius.** Fault injection into the host that also runs the grader.
- **Timeouts.** Hard-coded timeouts shorter than the validators' own polling.
- **Weak grading.**
  - Structural-only grading for behaviour-defined competencies such as NetworkPolicy.
  - Keyword-grep evidence checks.
  - Dead code inside validators.
- **Setup hygiene.**
  - Non-idempotent setups.
  - Setup-time Internet fetches.
  - Tools referenced but never installed.
- **Portability.** Hard-coded node names that differ across backends.
- **Security.**
  - An unauthenticated, root-executing HTTP API with wildcard CORS (`server/main.go:68-79`).
  - A privileged container presented as a "node".
- **Content hygiene.**
  - Solutions in the user-visible hint field.
  - **Any K16S scenario wording, ids, flag names, file paths or scripts.** These are a licensing issue and a contamination risk: the repo is public with full solutions in its hints.

## 10. Recommended adaptation pattern

KOPS proposes three backends (`docs/backend-design.md`):

| KOPS backend | Substrate | What it borrows from K16S (ideas only) | What it does differently |
|---|---|---|---|
| **A `kind`** (object-level) | kind cluster | Task triple; capability tag; evidence plus live-state checks | Object-level tasks only. Namespace- or cluster-level reset. Grader outside the agent's shell. Behavioural NetworkPolicy probes. Offline, pinned artefacts |
| **B1 `kind-node`** (cheap system-level) | kind node containers with systemd, kubelet, containerd, a static-pod control plane and stacked etcd, plus sshd and etcd tools from a KOPS-built derived image | The §7.2 checklist; the ssh-to-node candidate path; the separate runtime-exec grader path | **The control plane lives inside a disposable container**, not on the host. Whole cluster recreated or restored per trial. Unprivileged agent workstation. Fidelity limits (modules, swap, AppArmor, reboot) declared in scenario metadata |
| **B2 `vm`** (high-fidelity system-level) | Incus **VM** instances on a copy-on-write pool, golden images per Kubernetes version, snapshot restore per trial | The observation that Incus is operationally convenient, plus its snapshot primitives (which K16S never used) | Own kernel per node: modules, sysctls, swap, AppArmor, reboot and kubeadm upgrade become real. Every node, control plane included, is restored from a snapshot |

**Why KOPS does not fork K16S.**
1. **License.** A fork inherits PolyForm NC and blocks a permissive public release (§9).
2. **Different product.** K16S is a human exam UI: sessions, timer, browser terminal, desktop. KOPS is a deterministic agent harness that needs a programmatic backend interface, structured results, reference solutions and repeated trials. Little of K16S's code maps onto that.
3. **Grading quality.** The verification layer has timing-dependent and structural-only checks (§5) that KOPS would have to rewrite anyway.

**Why KOPS does not adopt privileged-LXC workers with a host control plane.**
- **R1 — every node, including the control plane, must be resettable.** In K16S the control plane *is* the host. Control-plane tasks (API server, scheduler, etcd, kubelet hardening, certificates) mutate state that can only be recovered by rebuilding the machine. Deterministic, repeated trials need restore in seconds to minutes per trial. B1 recreates containers; B2 restores snapshots of every node.
- **Grader isolation.** K16S's grader runs on the node being broken and depends on its API server. A failed or partially fixed task can corrupt grading of the same or later tasks. KOPS runs the grader from outside the cluster's failure domain and treats "API unreachable" as a scored outcome, not a grader crash.
- **Isolation from the host.** Privileged, unconfined, capability-complete containers with read-write `/proc` and `/sys` give node root equal to host root. That is unacceptable when the actor is an autonomous agent with shell access to nodes. B1 keeps kind's standard container boundary and gives the agent an unprivileged workstation. B2 puts a hypervisor boundary around each node.
- **No fidelity gain over B1.** Privileged LXC workers share the host kernel exactly as kind nodes do, so modules, swap, AppArmor and reboot are equally unavailable. For those, KOPS moves to real VMs (B2) instead of widening host privileges. K16S's own coverage (§7.3) shows the shared-kernel tier pushes hard tasks onto the host.

**Net pattern.** Take K16S's *task contract* and *capability-aware scoring*. Take its *LXC settings list* as a checklist of kernel concerns. Take its *two-channel access* (candidate ssh vs grader runtime-exec). Discard its topology, reset model, grader placement and all content.
